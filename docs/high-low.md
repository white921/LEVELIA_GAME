# ハイアンドロー ブラウザ版

更新日: 2026-10-03

## 現在の範囲

- React / TypeScript / Motionで動く1人用ゲーム。
- 通常トランプ52種類から毎回独立に抽選し、ジョーカーは使わない。
- 現在のカードより次のカードが高いか低いかを予想する。
- Aを最大、2を最小とする。スート（マーク）に強弱はない。
- 同じ数字は引き分けとし、連勝数と精算倍率は変化しない。
- 正解で連勝数を1増やし、不正解は払い戻しなしでゲーム終了とする。
- 抽選済みのカードを除外しない。同一カードが続けて出ることもある。新規ゲームは残り山札を記録せず、過去の山札記録だけをそのまま残す。
- Aまたは2が次の基準カードになった場合は、勝敗や連勝を増減させず次のカードまで自動で進める。
- 1〜4連勝では精算または次の予想を選べる。1ゲーム内では5連勝で自動精算して終了する。最高連勝の記録は次のゲームへ引き継ぐ。
- 賭け金は100・1,000・10,000 LIA。新規ゲームは現在のカードと選択方向の勝率に応じた倍率を使い、連勝ごとの還元係数は99.5→100.5→101.5→102.5→103.5%。HIGH・LOWボタンには次の勝利時配当、精算ボタンには現在受け取れる額を表示する。賭け金選択画面には倍率計算の詳細を載せない。
- 旧固定配当の計算処理は削除。進行中の旧ゲームが0件であることを確認して移行する。過去のゲーム・精算履歴は変更しない。新規ゲームは `rules_version=3`。
- Discord Activity内ではEmbedded App SDKの `identify` scopeで本人を認証する。
- Discordで検証した本人の`accounts.wallet`だけを使用し、抽選・勝敗・精算はActivityサーバーを正とする。
- 最高連勝数は、本人の`levelia_game_high_low_hands`をID順に読み、敗北（`status = 'lost'`）の直後で区切った各区間の`streak`合計の最大値をDBから取得する。負けたゲームで敗北前に積み上げた勝利もその区間に含む。5連勝での終了・途中精算・引き分け・期限切れでは区切らず、負けたときだけ連勝が途切れる。例：5勝で終了→次のゲームで2勝→敗北なら最高7連勝。過去最高は敗北後も残す。既存のDB記録にも同じ集計を適用し、データの書き換えやローカル記録の取り込みは行わない。認証前や取得できない場合は「—」と表示する。
- 通常ブラウザは画面確認用とし、ゲーム結果は生成しない。実プレイはDiscord Activity内で行う。
- 切断から5分間は復帰できる。期限後は1勝以上なら現在倍率で自動精算し、0勝なら払い戻しなしで終了する。1ゲームの絶対期限は30分。
- 賭け金は残高から消滅し、配当は新規発行する。LEVELIA Gameの履歴用口座残高は変動させない。

## 安全性

- 1ユーザーにつき進行中ゲームは1件だけ。
- 変更APIは`requestId`で二重処理を防ぎ、`version`で古いタブからの操作を拒否する。
- 変更APIの通信失敗・サーバーエラーは同じ`requestId`で1回だけ再試行する。結果が不明な場合や古い状態を検知した場合はサーバーのゲーム状態を再取得し、確認できるまでは新しい賭けを受け付けない。
- 自動精算はゲーム単位で失敗を切り分け、後続のゲームを処理する。失敗したゲームはトランザクションを取り消して次の巡回で再試行する。
- 残高、ゲーム状態、専用台帳、`actions`履歴は同一DBトランザクションで確定する。
- 運命改変、カード選択にはサーバーの暗号学的乱数を使う。
- 凍結口座とサブアカウントは新しいゲームを開始できない。ただし、運営者指定のユーザーID `1551725849009586270` のみサブアカウントの制限を免除する。プレイ許可リスト・口座凍結・残高・進行中ゲームの制限は通常どおり適用し、賭け金と配当にはその本人の口座を使う。
- 配当履歴は「LEVELIA Gameからの送金」と表示する。履歴上の相手IDは`1552246348756025344`。この口座は事前に存在する必要がある。マイグレーションは口座の作成・ユーザー情報変更を行わず、ゲーム中もこの口座残高は変更しない。

## 連勝型の配当と補正

`F=1` で開始し、勝利時だけ `F←F/q` とする。現在のランクをr（2〜14）とし、HIGHならW=14-r、LOWならW=r-2、L=12-Wとすると、引き分けを除く正確な勝率は `q=(1000W+L)/(1000(W+L))`（既存の1/1000救済を含む）。基準カードは3〜Kなので両方向を選べる。同ランクは毎回1/13。引き分けはF・連勝・精算額を維持する。

精算額は `floor(賭け金 × F × 連勝段階の還元係数 × 補正係数)`。FはBigIntの既約分数として保存し、最終額の計算でだけ切り捨てる。連勝係数と補正係数を勝つたびに累乗しない。表示した精算額を手動・5勝・切断時のいずれでもそのまま精算する。

- 目標平均還元率から `補正係数 = 目標(%) ÷ 102.58118179645447` を計算し、百万分の1単位に丸める。目標98%は係数0.955341、101%は0.984586となる。連勝するほど有利な構造を維持する。
- 基準は独立抽選版の心理シミュレーション（36,000セッション、3,510,601ゲーム）の「中間・目標型が多い構成」。モデルIDは `iid-behavior-engaged-20261003-v1`。実際の人の行動に適合したモデルではない。再現用スクリプト・結果は `output/iid-target-rtp-20261003/`。賭け金総額で重み付けした平均を使用する。
- 移行時は従来の補正係数1を維持し、目標は未指定として表示する。目標100%を設定すると基準配当より減額される。
- 目標は0.0001〜1000%、小数点以下4桁まで。新しいゲームの開始時に値と設定バージョンを保存し、途中変更・再起動で進行中の配当は変えない。
- 設定はDBの `levelia_game_high_low_settings`、指定目標・校正モデルID・変更者・前後の補正値・操作IDは `levelia_game_high_low_setting_changes` に保存。同じDiscord interaction IDの再送では設定を書き直さない。
- 総合還元率は精算行動や賭け金構成による推定値。補正後に行動が変わる可能性もあり、指定値の総合還元率を保証しない。
- 既存の口座上限2,147,483,647 LIAを維持する。勝利時に上限を超える選択はカードを引く前に拒否する。配当を上限まで切り下げることはしない。この制約は上限なしの過去シミュレーションとは異なる。現在配当は既存の精算経路で受け取れるが、別経路の入金で口座上限に達した場合は従来どおり精算を保留する。

## Discord管理コマンド

```text
/ハイロー還元率 確認
/ハイロー還元率 設定 目標:98
/ハイロー還元率 設定 目標:100
```

指定サーバー内で、次のいずれかのロールを持つメンバーだけが確認・設定できる。管理者権限やゲームのプレイ許可リストによる迂回は認めない。応答は実行者だけに表示する。

| ロール | ID |
| --- | --- |
| 英傑 | 1534637252620062881 |
| 皇帝 | 1534636370717573150 |
| システム支配人 | 1534879870532849846 |

本番反映時の手順:

1. `npm run migrate` で追加テーブルと配当状態列を作成する。再実行しても既存設定をリセットしない。
2. このアプリ自身の `DISCORD_PUBLIC_KEY` と `GUILD_ID` をサーバーへ設定する。公開鍵はDeveloper PortalのGeneral Informationから取得する。
3. 公開サーバーの `/api/discord/interactions` をInteractions Endpoint URLに設定する。署名と時刻を検証し、DB操作前に非公開の遅延応答を返す。
4. このアプリ自身の `DISCORD_BOT_TOKEN` を使い、`npm run commands:register` で登録内容をプレビューし、`npm run commands:register -- --apply` で旧管理コマンドを同じIDのまま改名・更新する。既存のActivity起動コマンドを一括上書きしない。
5. 実行権限は毎回サーバー側で検証する。コマンド候補も3ロール以外に非表示にしたい場合は、Discordのサーバー設定→連携サービスで、このコマンドを3ロールだけに許可する。

HTTPによるInteractions受信はGateway受信と排他的なので、同じアプリで別のコマンド受信プロセスを動かしている場合は切替前に確認する。旧・新サーバーを混在させたまま新ルールのゲームを開始しない。

仕様参照: [Discord Interactions](https://docs.discord.com/developers/interactions/overview)、[応答と遅延応答](https://docs.discord.com/developers/interactions/receiving-and-responding)、[コマンド権限](https://docs.discord.com/developers/interactions/application-commands)。

## 週間ランキング

- `HIGH_LOW_LEADERBOARD_RESET_AT`にタイムゾーン付きISO日時を設定すると、その時刻でランキングだけをリセットする。時刻到来までは従来の集計を維持し、到来時にキャッシュを失効する。以降は週の開始と設定日時の遅い方から正解・精算を集計し、倍率は設定日時以降に開始したゲームだけが対象。ログ・台帳・残高・通算最高連勝は変更しない。表示期間も実際の集計開始日に合わせ、翌週から通常の月曜始まりに戻る。今回の開始は`2026-10-04T00:00:00+09:00`（初回は10月4日の1日間）。

- HIGH&LOW画面の「週間ランキングを見る」またはヘッダーの「ランキング」から、ゲームを開いたまま週間最高連勝・週間最高精算倍率を確認する。白系の背景に2枚の羊皮紙を並べ、PCは左右、SPは上下に表示する。閉じる・Escapeで元のゲームへ戻り、進行状態とheartbeatを維持する。
- 週は日本時間の月曜0:00以上、翌月曜0:00未満。最高連勝は週内の予想結果だけを時系列に数え、精算・引き分け・期限切れでは切らず、不正解でリセットする。進行中ゲームも対象で、前週の正解数は持ち越さない。
- 最高精算倍率は週内の精算額÷賭け金。手動精算・5連勝時・切断時の自動精算を含み、未精算の見込み額・敗北・0勝失効は含めない。賭け金100/1,000/10,000の実受取額から小数4桁まで正確に比較する。
- 各部門の上位3人を同時表示。同じ値は同順位（1位・1位・3位）で、同順位内の並びはユーザーID順。枠は3人までとし、記録が足りない枠は「挑戦者募集中」とする。
- 表示名・アイコンはこのアプリ自身の`DISCORD_BOT_TOKEN`と`GUILD_ID`でDiscordのメンバー情報を読み、サーバーのニックネーム・専用アバターを優先する。専用アバターがなければ通常アバター、未設定ならデフォルトアバター。取得失敗時は既存`accounts.user_name`と前回の画像またはデフォルト画像を使う。両部門で重複を除いた最大6人だけを取得し、5分キャッシュ・同時要求の共有・失敗時の待機を設ける。口座情報を変更せず、Bot Tokenをブラウザへ返さない。
- `GET /.proxy/api/high-low/leaderboard`はDiscord認証・既存アクセス制限を通し、本人の順位は検証済みIDから決定する（画面は上位3人のみ）。実残高と仮想残高で集計元・キャッシュを分離する。
- サーバーはプロセス内で5分間の集計結果を共有し、同時要求も1回の集計にまとめる。期限後の最初のアクセスで再集計し、週が変わる時点でも失効する。複数プロセスの場合は各プロセスで集計する。
- クライアントは開いた時に取得し、サーバーが返す次回更新時刻に合わせて通常5分ごとに再取得する。非表示タブ・閉じたランキングでは停止し、復帰時に期限切れなら再取得する。更新失敗時は同じ週の前回結果とエラーを表示する。
- `npm run migrate`で通常・仮想それぞれのcommandsに`(action, created_at)`、handsに`(settled_at)`のインデックスを追加する。新しい集計テーブルや外部キャッシュは使わない。
- 週間連勝の再集計は`commands`の保存済み予想結果に依存するため、当週の記録を削除しないこと。
- SQL結合テストは破棄可能な専用DB `levelia_leaderboard_test` を`TEST_LEADERBOARD_MYSQL_URL`で指定する。テストはそのDBのテーブルを作り直す。

## 起動

```sh
npm install
npm run migrate
npm run dev
```

表示されたローカルURLをブラウザで開く。通常は `http://127.0.0.1:5173`。

## 検証

```sh
npm run activity:test
npm run build
PORT=3000 npm start
```

`activity-dist/` に静的ファイルが生成される。通常ブラウザではゲームをプレビューできるが、Discord認証と残高表示はDiscord Activity内でのみ動作する。

RailwayではActivity WebサービスのBuild Commandを `npm ci && npm run activity:build`、Pre-deploy Commandを`npm run migrate`、Start Commandを `npm run activity:start` とする。VariableとPublic NetworkingのTarget Portをともに `3000`、Healthcheck Pathを `/health` に設定する。

Activity WebのVariableには `DISCORD_CLIENT_ID`、`DISCORD_CLIENT_SECRET`、`MYSQL_URL` も設定する。Client SecretとMySQL接続情報はサーバー内だけで使用し、Viteの公開環境変数にはしない。

## 日次の取引履歴・通知

- 賭け金・配当・自動精算の残高更新、専用台帳、`actions`は毎回同じDBトランザクションで保存する。内部の個別記録は監査用に維持する。
- 利用者向けの取引履歴はKARUMA側で1人1日1件にまとめ、ハイローの個別記録や表示切り替えは出さない。当日分は翌日午前1時の集計後に表示する。
- 集計は日本時間0:00〜24:00の実際の残高増減。翌日午前1時に対象者へDMで残高増減・賭け金合計・受取合計を送る。日をまたぐ賭け金と配当はそれぞれ実際に記録された日に含める。
- 実残高の`levelia_game_high_low_ledger`だけを集計する。仮想プレイ・他の送金・報酬は含めない。報告処理で残高や元の履歴を再更新しない。
- 日次履歴・通知処理とマイグレーションはKARUMAリポジトリに置く。仕様・導入手順の正本は同リポジトリの`docs/high-low-daily-history.md`。
- 以前検討した利用単位の履歴、アプリ全体の接続確認、個別明細切り替えは採用しない。この機能のためのActivityクライアント/API変更は不要。

## 期間指定のカジノ統計

管理3ロール（英傑・皇帝・システム支配人）は、本人だけに表示される `/カジノ統計` で実台帳の期間集計を確認できる。

```text
/カジノ統計 開始日:2026-10-04
/カジノ統計 開始日:2026-10-01 終了日:2026-10-04
/カジノ統計 開始日:2026-10-01 終了日:2026-10-04 ユーザー:@ユーザー
```

- 日付は `YYYY-MM-DD` の日本時間。開始日だけならその日の0:00〜24:00、終了日も指定した場合は終了日の24:00までを含む。
- 未来までを指定した場合は実行時点までを集計し、途中であることを表示する。
- 最高利益と最大損失はプレイヤー別の純損益。サーバー全体損益は全プレイヤーの純損益合計。
- `ユーザー` は任意。指定時は全体の最高・最低ではなく、そのユーザーだけの純損益・賭け金合計・配当合計・還元率を表示する。
- 還元率は期間内の配当合計÷賭け金合計。実残高の `levelia_game_high_low_ledger` だけを使い、仮想プレイ、送金、報酬、残高調整は含めない。
